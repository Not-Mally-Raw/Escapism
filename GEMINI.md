# Project Tracking Rule

Before starting any new phase or determining the next task, ALWAYS read `docs/Project_Timeline_and_Checkpoints_v2.md` in full. If the file cannot be found at that path, STATE THIS EXPLICITLY before proceeding — never assume or reconstruct project status from memory alone.

This document is the source of truth for roadmap, completion status, and open verification items (Part C).

## Pre-Flight Status Validation
Any time you are about to claim an item is "done", "verified", or "complete", you MUST cross-check that claim against the tracker's current status first. If the tracker says ⚠️ or 🔶 for something you are about to call done, you must surface this contradiction explicitly before proceeding. Never silently override the tracker's state.

## MANDATORY WRITE-BACK
Whenever a task closes an item from Part C, or a stage's status changes (✅/🔶/⚠️/⬜), UPDATE the tracker file itself as part of that task's deliverable — not as a separate, optional follow-up. 
- A stage is not "done" until both the code is verified AND the tracker reflects it. 
- If new gaps are discovered during a task, ADD them to Part C immediately, in the same session, not deferred to "later".
- Never mark an item ✅ DONE, VERIFIED in the tracker without pasting the raw evidence that justifies it in the same response, matching this project's established discipline. A tracker update without evidence is itself a violation of the rule this file exists to enforce.
